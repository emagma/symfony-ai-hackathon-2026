# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A monorepo of three applications and their packages, started by one `docker compose` stack on the developer's computer:

A folder that is not a valid skill is left out, never fatal | - |

## Development commands

Everything is driven by [Castor](https://castor.jolicode.com/) from the **host** (the tasks shell out to `docker compose`; they refuse to run inside a container, and with `CI=true`). `castor list` is the authoritative list - there is no Makefile.

```bash
castor init                  # fresh clone → running stack, verified (--skip-build, --skip-db, --no-fixtures, --skip-assets, --skip-hosts, --yes)
castor init:env              # regenerate .project.local.ini + docker/.env (drops a tunnel)
castor init:verify           # shop 200, realm served, /_mcp 401 + RFC 9728 pointer, grants in the token, the Anthropic key in the containers
castor init:info             # URLs and credentials

castor docker:up|down|logs [service]|build|shell
castor shop:console <cmd>    # Symfony console of the shop (args forwarded verbatim)
castor shop:db               # drop/create/migrate/fixtures + the MCP service account
castor shop:assets           # yarn install && yarn build + assets:install
castor mcp:console <cmd>     # Symfony console of the MCP server
castor mcp:db                # create-if-missing + migrate the server's own database
castor mcp:permissions       # the grants every tool declares (--format=json for scripts)
castor mcp:shop-extensions   # mcp:shop-extensions:check: MCP_SHOP_EXTENSIONS vs what the shop publishes (also in init:verify)
castor mcp:sylius-version    # mcp:sylius-version:check: MCP_SYLIUS_VERSION vs the shop's Sylius version (also in init:verify)
castor mcp:sylius-api-routes # regenerate the route table at the end of packages/mcp-sylius-bundle/docs/developer-guide.md from the Sylius tags (TAGS, network)
castor mcp:bench             # the "autonomous agent" scenario against the shop
castor mcp:qa                # the QA scenarios (apps/mcp-server/tests/Qa) against a throwaway shop (shop_qa DB, shop-qa container) loaded with the fixtures; --filter, --keep; --shop-url/--sylius-version/--shop-extensions for another 2.x shop already loaded
castor keycloak:init         # realm imported + roles cover the grants (--recreate re-imports)
castor keycloak:realm        # regenerate docker/keycloak/realm-sylius.json from .castor/keycloak-realm.php
castor chat:up|info|console <cmd>
castor tunnel:up|info|down   # Cloudflare quick tunnels for mcp-server + Keycloak's sylius realm (Claude web, ChatGPT)

castor quality:all           # plugins + mcp-server + chat + shop: ECS, PHPStan (level max + baseline), PHPUnit
castor mcp:quality:deptrac   # the boundaries between the server's bundles (apps/mcp-server/deptrac.yaml, code and tests, no baseline); part of mcp:quality and of CI
castor plugin:quality | mcp:quality | chat:quality | shop:quality   # one at a time (…:ecs --fix to apply)
bin/ci/mcp-server.sh | chat.sh | shop.sh  # the CI quality jobs (plain shell, no castor: PHP 8.4 + composer, Node 22 for the chat); they discover the packages present
bin/ci/packages.sh lowest|highest  # each package that carries its own tools (PHPUnit, PHPStan, coding standard in its require-dev), alone in a throwaway copy: bin/ci/package.sh <package> <lowest|highest>
```

## Configuration

`.project.ini` is the source of truth; `bin/resolve-env.sh` resolves it into the git-ignored `.project.local.ini` and `docker/.env`. Both are absent from a fresh clone. **`resolve-env.sh` preserves existing values**, `compose_file` included: a clone resolved before an overlay existed keeps its old stack, and `castor init:env` warns about the drift. Delete the line from `.project.local.ini` to adopt the default.

The shop container runs in **prod without debug** by default (`[apps.shop] app_env` / `app_debug` in `.project.ini` → `SHOP_APP_ENV` / `SHOP_APP_DEBUG`): no profiler, compiled container, the Sylius API enabled in every env (`config/packages/sylius_api.yaml`, the standard only had it in dev). After a config change in the shop: `castor shop:console cache:clear`. mcp-server and chat stay in dev.

The shop's fixtures are **reproducible, but for two points**: `apps/shop/config/packages/sylius_fixtures.yaml` seeds the default suite (`deterministic_seed` listener; `src/Fixture/random_int.php` routes the Sylius factories' `random_int()` to the seeded `mt_rand()`), so every `castor shop:db` loads the same catalog, stock, customers and orders, with dates relative to the run. Two loads still differ on the `token_value` of the 25 orders and on the 3 promotions of the Sylius suite (description, exclusive flag, percentage, threshold): the seed does not fix them. A test or a scenario must not rely on an order's token or on those promotions' values. The same file and `src/Fixture/QaScenarioFixture.php` add the data of the QA test scenarios (`apps/mcp-server/tests/Qa`). Anything appended to the suite after the existing fixtures keeps the rest identical; a change before them reshuffles everything that follows.

Default `compose_file`: `compose.yaml:compose.dev.yaml:compose.chat.yaml`. `compose.tunnel.yaml` is appended by `castor tunnel:up` through a managed block at the end of `docker/.env`.

`[apps.mcp-server] shop_extensions` → `MCP_SHOP_EXTENSIONS` (comma-separated, the names the installed bundles declare; empty here, as the server's default; an unknown name stops the server): a tool marked `#[RequiresShopExtension]` is hidden from `tools/list` and answers `shop_extension_disabled` unless its extension is listed. Read at runtime (no cache clear): `castor init:env` then `castor docker:up` to recreate the container.

`[apps.mcp-server] sylius_version` → `MCP_SYLIUS_VERSION` (`2.0`…`2.3`, optional patch; `2.3` by default, an unsupported value stops the server): the shop's Sylius line, configured, not discovered. A tool marked `#[RequiresApiFeature]` is hidden and answers `sylius_version_unsupported` on a line without that endpoint (`ApiFeature` holds the version of each). The routes of each line: the end of `packages/mcp-sylius-bundle/docs/developer-guide.md`, regenerated by `castor mcp:sylius-api-routes`.

LLM API keys for the chat live ONLY in `.project.local.ini` (`[infrastructure.ai.<provider>] api_key`), never in `apps/chat/.env` (committed, and ignored anyway: compose sets the variables). The Anthropic key also serves the server's own model calls (tasks, fraud agent).

## Docker

One FrankenPHP (PHP 8.4, Node 22) image `${DOCKER_REGISTRY}/php:dev` (`emagma-agent-backend/php:dev`, built locally, never pulled) built from `docker/php/Dockerfile` (**build context = the repository root**, `.dockerignore` keeps the secrets and vendors out), shared by the three apps, which differ by `working_dir` and `command: ["--config", "/srv/app/apps/<app>/docker/Caddyfile", "--adapter", "caddyfile"]`. Services: `shop`, `shop-worker` (Messenger consumer), `mcp-server`, its three Messenger consumers (one per kind of job: `mcp-tasks-worker` for `mcp_tasks`, `stop_grace_period: 10m`; `mcp-agents-worker` for `mcp_agents` and `async`, the emails; `mcp-scheduler` for `scheduler_mcp_agents`, one replica), `chat`, `database` (MySQL 8.4 - **not MariaDB**: with doctrine/dbal 4 the Sylius migrations skip themselves on MariaDB), `keycloak` (26.1, `KC_HOSTNAME=http://keycloak:8085` + `/etc/hosts` entry), `mailpit`.

`docker/database/init-mcp.sh` creates the server's database and user on a **fresh volume only**; `castor mcp:db` does `database:create --if-not-exists` for older volumes, and stops the three consumers while it migrates.

## Keycloak

The realm is edited **only** in `.castor/keycloak-realm.php` (its `GRANTS` list by hand, from `castor mcp:permissions --format=json`); `castor keycloak:realm` regenerates `docker/keycloak/realm-sylius.json` from it. Apply with `castor keycloak:init --recreate` - a plain restart keeps the container's H2 state and silently skips the import. Clients: `mcp-llm` (Claude web / ChatGPT, public + PKCE), `mcp-cli` (Claude Code, loopback callback; `.mcp.json` names it), `mcp-testchat` (the chat), `mcp-tasks` (confidential, background tasks), `dev-cli` (password grant, scripts only). Demo users: password = username; `admin` holds the composite realm role `sylius-admin` (every MCP grant). The Sylius admin UI keeps its own `form_login`: there is no admin SSO. The realm file carries `${NAME:default}` placeholders Keycloak resolves from its environment at import: the demo users' password (`DEMO_USERS_PASSWORD`), the `mcp-tasks` secret (`MCP_TASKS_CLIENT_SECRET`), the public URLs of the chat and the server (`CHAT_PUBLIC_URL`, `MCP_PUBLIC_URL`); unset, the local values. Never pass one empty: Keycloak imports it as is. `castor tunnel:up` publishes the `sylius` realm only, through `keycloak-public` (`docker/tunnel/Caddyfile`); while it is open, the demo users are public.

## CI

Two CIs run the same gates: `.github/workflows/quality.yml` (push on `main`, pull requests, by hand; `contents: read`, no secret) and `.gitlab-ci.yml` (merge requests, every branch push, tags). Both only call `bin/ci/mcp-server.sh`, `bin/ci/chat.sh`, `bin/ci/shop.sh` and `bin/ci/packages.sh` (lowest and highest dependencies, the packages that run alone): ECS, PHPStan, deptrac, PHPUnit, one job per composer root, plus the chat's JavaScript tests (`node --test`, `node --check public/app.js`). The scripts discover the packages: the server's bundles are the `packages/mcp-*-bundle` and the hackathon bundle present, the shop's plugins the `packages/sylius-mcp*-plugin` present; a step written for a package absent here skips itself.

The server's bundles and the shop's plugins are also proven on Symfony 8.1 (the `symfony: [lock, '8.1']` matrix on GitHub, the `-symfony-8.1` jobs on GitLab): with `SYMFONY_REQUIRE=8.1.*`, `bin/ci/lib.sh` resolves with `composer update -W` instead of the lock, which stays on 7.4, and checks the version installed; that rewrites tracked files, so the scripts refuse it outside CI unless `CI_ALLOW_COMPOSER_UPDATE=1` (on a throwaway copy only).

To run a script locally, in a throwaway container of the stack's image mounted on the repository:

```bash
docker run --rm -u "$(id -u):$(id -g)" -e COMPOSER_HOME=/tmp/composer -v "$PWD":/srv/app -w /srv/app \
  --entrypoint '' emagma-agent-backend/php:dev bin/ci/mcp-server.sh
```

## Known traps

- The generic bundles ship neutral defaults and this stack keeps its own value in `config/packages/`: `emagma_mcp_core.redaction.marker` (`__REDACTED_BY_SYLIUS_ASSISTANT__`, what the audit already holds - changing it makes older scrubbed entries unrecognised). The audit table is the bundle's default, `mcp_audit`.
- The server reads its identity provider from two agnostic variables, defaults of the auth bundles: `MCP_AUTH_ISSUER_URL` (`emagma_mcp_auth.authorization_servers`, the realm as the remote client reaches it) and `MCP_AUTH_USERINFO_URL` (`emagma_mcp_auth_keycloak.userinfo_url`, backchannel). `compose.yaml` derives both from `KEYCLOAK_PUBLIC_URL` / the tunnel URL, which stay the variables of the Keycloak container.
- The MCP SDK finds its PSR-17 factories by discovery: `apps/mcp-server` requires `nyholm/psr7` for it. Without an implementation, every request to `/_mcp` answers 500.

- A new `packages/mcp-*-bundle` is a class `Emagma<Name>Bundle` extending `AbstractBundle` (alias `emagma_mcp_<name>`, configuration in the class, services written out in `config/services.php`, no autowiring scan), and is wired in four places: the path repository of `apps/mcp-server/composer.json` (`only` its package, `options.versions` at the version of every package, `0.1.0`, and the requirement `^0.1`: without the version the lock records the branch name), `config/bundles.php`, `PACKAGES` in `.castor/mcp.php`, and the paths (`src`, `tests`, `migrations` when it ships some) and layers of `apps/mcp-server/deptrac.yaml`. The CI scripts find it on their own; a package whose `require-dev` holds PHPUnit, PHPStan and the coding standard is also checked alone, on its lowest and highest dependencies, by `bin/ci/packages.sh` (`bin/ci/package.sh <package> <lowest|highest>` to run one).
- The conventions of the tools are abstract test cases (`Testing/Conformance` of the core and of the Sylius bundle): a bundle that brings tools extends them in its own `tests/Unit/Conformance`, and `apps/mcp-server/tests/Conformance` replays them on what `ServerSources` assembles from every bundle (`ServerSourcesTest` fails when a scan shrinks below `MIN_TOOL_CLASSES` / `MIN_OUTPUT_CLASSES`).
- The Sylius bundle alone talks to no shop: a line bundle (`mcp-sylius-v2-bundle`) must be registered, and a version no registered line serves stops the server on the first request. A new 2.x minor is added to `Sylius2Line::VERSIONS` once its routes are checked; a new major is a new bundle. The base's tests never name a line's adapter (deptrac): they use `DefaultLayoutAdapter`.
- A bundle brings what is its own as prepended defaults (`prependExtension()` of its bundle class): the Sylius HTTP clients and notice, each bundle's tool namespace on the server the core attaches to (`McpCoreConfig::prependServerConfig()`, the core's helper), the log channels (each named after its bundle's alias, `emagma_mcp_core`, `emagma_mcp_core_authorization`, `emagma_mcp_audit`, a suffix for a second channel of the same bundle), the audit's Doctrine mapping. The server's instructions are assembled by the core from every service tagged `emagma_mcp_core.instruction` (`#[AsMcpInstruction(priority)]`, highest first): the Sylius conventions at 100, the guidelines' intents and the screens at 0; reorder with the tag's priority, change a text with a decorator. What stays in `apps/mcp-server/config` is this installation's: the firewall, the server's identity and transports, trusted clients, URLs.
- The shop plugin is `packages/sylius-mcp-plugin` (Composer `emagma/sylius-mcp-plugin`, the Sylius 2.x line). A clone that installed the shop when it was `packages/sylius-mcp-v2-plugin` relinks its vendor with `composer install` in `apps/shop`, then `castor shop:console cache:clear`.
- Flex rewrites `config/bundles.php` on `composer update` and drops its comments.

- `max_execution_time=60` in the shared `app.ini` bounds an elicitation on the MCP server; the chat's modal auto-accepts at 30 s.
- PHPUnit in a container: `phpunit.xml.dist` forces `APP_ENV` through both `<server>` and `<env>` (Dotenv and KernelTestCase read `$_SERVER`/`$_ENV` in opposite orders, and the container exports `APP_ENV=dev`). The functional suite of the MCP server needs `memory_limit=-1` (it compiles the discovery of every tool). Its Messenger transports are in memory there (`config/packages/messenger.yaml`).
- The MCP server's emails and notifications go through the `async` transport: nothing reaches Mailpit while `mcp-agents-worker` is down, and `alerted: true` in `list_agent_reports` means queued, not delivered.
- The chat shows tokens, and a cost only when it is given a price source (`Catalog\PriceBook`); this stack gives none. Its tracer is a no-op without a trace endpoint.
